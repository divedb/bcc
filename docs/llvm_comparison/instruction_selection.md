# Instruction Selection: LLVM vs bcc

Covers how LLVM turns (optimized) IR into target instructions: the
SelectionDAG path, the GlobalISel path, TableGen-driven pattern matching,
target lowering hooks, and the supporting pieces (FastISel,
CodeGenPrepare). Then what "instruction selection" means for bcc today
(nothing in-tree — `llc` performs it), and a realistic native-ISel design
sized for bcc: GlobalISel-shaped, single target, C++ tables instead of
TableGen.

File inventories below were verified against `llvm-project` `main`
(Nov 2026).

---

## 1. LLVM's implementation

LLVM has two production instruction selectors plus a legacy fast path:

| Path | Representation | Entry point | Used by |
|---|---|---|---|
| **SelectionDAG** | per-block SSA DAG of `SDNode`s | `llvm/lib/CodeGen/SelectionDAG/SelectionDAGISel.cpp` | x86-64 at all levels; AArch64 at O1+; most targets |
| **GlobalISel** | whole-function generic MIR | `llvm/lib/CodeGen/GlobalISel/` (`IRTranslator.cpp` → `Legalizer.cpp` → `RegBankSelect.cpp` → `InstructionSelect.cpp`) | AArch64 −O0 default; AMDGPU everywhere; opt-in elsewhere |
| **FastISel** (legacy) | IR walk, per-instruction | `SelectionDAG/FastISel.cpp` + `X86FastISel.cpp` | limited -O0 use, being phased out |

### 1.1 SelectionDAG in detail

**Build** (`SelectionDAGBuilder.cpp`, driven from
`SelectionDAGISel::SelectAllBasicBlocks`): each basic block is lowered
independently into a DAG of `SDNode`s (`SelectionDAG.cpp`). `SDValue`
= (`SDNode*`, result#). Values are typed with `EVT`/`MVT` machine value
types (`i32`, `i64`, `f64`, vectors…); constants are uniqued in the DAG.
Calls and other IR instructions with side effects become `TokenFactor`
chains — a serializing edge through memory operations that preserves IR
semantics inside the block.

**Type legalization** (`LegalizeTypes.cpp` dispatcher →
`LegalizeIntegerTypes.cpp` / `LegalizeFloatTypes.cpp` /
`LegalizeVectorTypes.cpp` / `LegalizeTypesGeneric.cpp`): every operation
on a type the target doesn't support natively is rewritten —
*promote* (`i8 → i32` ops with explicit trunc), *expand* (`i64 → 2×i32`),
*scalarize* vectors. Targets declare the action per type via
`TargetLoweringBase::getTypeAction` decisions computed from
`TargetLowering::getTypeConversion`; e.g. x86 promotes `i1/i8/i16`
arithmetic to `i32` (`X86ISelLowering.cpp` sets
`setOperationAction(ISD::ADD, MVT::i8, Promote)`).

**Operation legalization** (`LegalizeDAG.cpp`): same idea per *opcode* —
`LegalizeSimple`, `LegalizeExpand` (e.g. `sdiv` by constants, rotates),
`Custom` (`TargetLowering::LowerOperation` — in x86,
`LowerToTLSGeneralDynamic`, bit-field manipulation, etc., in
`X86ISelLowering.cpp` / `X86ISelLoweringCall.cpp`).

**DAG combination** (`DAGCombiner.cpp`, ~14k lines): runs between every
phase (`run function`, `run on legal types`, `run on legalized ops`).
Target-independent identities (fold constants through ops, `trunc(sext)`
elimination, load folding into consumers) + target hook
`SelectionDAGTargetInfo::PerformDAGCombine` (x86:
`X86ISelDAGToDAG.cpp`/`X86ISelLowering.cpp` combine hooks — the famous
`lea`-shaping and compare-fusion rules live here).

**Selection** (`SelectionDAGISel.cpp: SelectCodeCommon` →
`MorphNodeTo`): pattern-matching over the DAG bottom-up using **match
tables generated by TableGen** from the target's `*.td` pattern
declarations — for x86 spread across `X86InstrArithmetic.td`,
`X86InstrCompiler.td`, `X86InstrCMovSetCC.td`, `X86InstrShiftRotate.td`,
`X86InstrFragments.td` (PatFrag reusable fragments), etc. A `.td` pattern
like:

```tablegen
def : Pat<(add GR64:$src1, (shl GR64:$src2, (i8 imm:$ shift))),
          (LEA64_32r ...)>;            // (x << k) + y  →  lea
```

compiles (`utils/TableGen/DAGISelEmitter.cpp` historically; now merged
into the TableGen backend set) into a decision tree inside
`X86GenDAGISel.inc` (build artifact) that `SelectCode` walks. Patterns
can carry C++ predicates (`Predicates = [UseNonTsx]`), `ComplexPattern`s
(matching addressing modes via C++ `SelectAddr` functions in
`X86ISelDAGToDAG.cpp`), and input/`imm` operand constraints. Matched
nodes are *morphed* in place (`MorphNodeTo`), recording fold-order for
debugging.

**Emission** (`InstrEmitter.cpp`): the selected DAG is emitted as
`MachineInstr`s into `MachineBasicBlock`s, in the order the (built-in)
scheduler's dependence graph permits (`ScheduleDAGSDNodes.cpp` — see
`instruction_scheduler.md`).

**CodeGenPrepare** (IR pass, `llvm/lib/Transforms/Scalar/
CodeGenPrepare.cpp`) deserves mention here: it pre-canonicalizes IR so
selection is trivial — most importantly it *forms addressing modes*
(`gep` chains + load folded into one pattern), sinks `inttoptr`, and
splits allocas. SelectionDAG's job is much simpler because CGP already
did address math shaping.

### 1.2 GlobalISel in detail

The modern path, designed for maintainability and testability
(`llvm/lib/CodeGen/GlobalISel/`, verified files):

1. **IRTranslator** (`IRTranslator.cpp`) — mechanical IR→MIR:
   every IR instruction maps to a *generic opcode* (`G_ADD`, `G_LOAD`,
   `G_ICMP`, `G_ZEXT`, `G_BR`, …) operating on unlimited virtual
   registers typed with `LLT` (low-level type: scalar bits or
   vector<numelts x bits>). No physical registers, no legality
   assumptions; aggregates become `G_IMPLICIT_DEF`+stores or
   `G_UNMERGE/G_MERGE`. `MachineIRBuilder.cpp` is the construction API.
2. **Legalizer** (`Legalizer.cpp` + `LegalizerInfo.cpp`,
   `LegalizerHelper.cpp`, `LegalityPredicates.cpp`) — iteratively
   rewrites illegal (type, opcode) combos using per-target rule tables
   (`X86LegalizerInfo.cpp`), actions: `Legal`, `WidenScalar`,
   `NarrowScalar`, `Lower` (to other ops), `Libcall` (to `__divdi3`-style
   runtime), `Custom`. TableGen-declared in `X86InstrGISel.td`-era
   descriptions. Artifacts of legalization (`G_ZEXT` of narrowed values
   etc.) are themselves legalized until a fixpoint.
   A **Combiner** (`Combiner.cpp` + `CombinerHelper*.cpp`) runs
   interleaved (target `.td`-generated rule tables via
   `GIMatchTableExecutor.cpp` — the same match-table machinery as SDAG's
   selector, reused).
3. **RegBankSelect** (`RegBankSelect.cpp`) — assigns each vreg a
   *register bank* (GPR vs. FP/vector on x86, via
   `X86RegisterBankInfo`/`X86GenRegisterBankInfo.def`), greedy or
   fast mode, with a repair cost model (inserting copies between banks).
4. **InstructionSelect** (`InstructionSelect.cpp` +
   `InstructionSelector.cpp`) — final rewrite of generic ops to real
   target `MachineInstr`s via TableGen-generated match tables
   (`GISelEmitter`-produced `.inc`, executed by
   `GIMatchTableExecutor.cpp`), now constrained by concrete register
   classes and immediates. Selection-time known bits come from
   `GISelValueTracking.cpp`.
5. **Localizer** (`Localizer.cpp`) — moves constants/copies near uses
   (SDAG's block-local model doesn't exist here).

Why GlobalISel exists: SDAG is per-block (cross-block values re-materialized),
hard to test, and C++/TableGen-entangled; GISel is a whole-function,
plain-MIR, staged pipeline where each stage has a verifier mode and the
match tables are uniform. Verified status (2026): default for AArch64 at
−O0 (and increasingly at higher levels), AMDGPU, and opt-in elsewhere
(`-global-isel`); x86 still SelectionDAG at all levels by default.

### 1.3 TableGen's role

`llvm/lib/Target/X86/X86.td` + `X86InstrInfo.td` define instructions
(operands, encoders via `X86InstrFormats.td`, predicates, sched classes);
patterns in `X86InstrCompiler.td`/`X86InstrArithmetic.td`/… map ISD/GMIR
nodes onto them. The *single source of truth* pays off: instruction
encodings, asm printer strings, disassembler tables, scheduler models,
and both selectors all generate from it. The cost is the TableGen
language itself and ~100k lines of generator code in
`llvm/utils/TableGen`.

## 2. bcc's implementation

There is no instruction selection in bcc. The pipeline is:

```
bcc codegen (AST→IR) → print .ll → llc (does ALL of: CGP, SDAG ISel,
  scheduling, RA, PEI, MC emission) → .s text → bcc-as (parses AT&T,
  encodes bytes, applies relocations) → .o
```

Implications:

- Selection *quality* is LLVM's (optimal patterns: `lea` shaping,
  `test` vs `cmp`, `setcc`+`movzx`, magic-number division, flags reuse —
  all present via `llc`).
- Selection *capability* is bounded by what survives the text round-trip:
  IR-level constructs bcc cannot express (varargs intrinsics
  `llvm.va_start`, aggregate-by-value ABI lowering, `long double` =
  `double` deviation, no inline asm, no intrinsics at all) are precisely
  the constructs a native selector would have to own.
- bcc's IR is already "generic machine IR"-like in the GlobalISel sense:
  unlimited SSA temporaries, a small opcode set, explicit casts. The gap
  to a `G_*`-style layer is small — mostly renaming decisions and giving
  `load/store/gep` target-friendly forms.

The `as/` library encodes x86-64 (REX/ModRM/SIB, rip-relative,
`RelType`/`RelModifier` fixups) but operates on *parsed text operands*,
not on any in-memory instruction representation shared with a compiler.

## 3. Comparison

| Aspect | LLVM SDAG | LLVM GlobalISel | bcc (native ISel, future) |
|---|---|---|---|
| Unit of selection | per-basic-block DAG | whole-function MIR | recommend: per-basic-block instruction list (no DAG) — see §5 |
| Legality | types+ops via TLI actions interleaved with combine | explicit Legalizer stage w/ rule tables | needed only for "types" x86-64 lacks: `i1`/`i8`/`i16` arithmetic promotion — a fixed, small set |
| Pattern source | TableGen → generated match tables | TableGen → GISel match tables | hand-written C++ pattern table (one target, ~50 patterns cover C int/FP/branch/mem) |
| Addressing modes | CGP + ComplexPattern (`SelectAddr`) | selector rules + CombinerHelper | explicit "address formation" pass over `gep` chains before selection |
| Testability | `-debug-only=isel`, `-view-isel-dags` | MIR-level unit tests (`llvm/test/CodeGen/AArch64/GlobalISel/*`) | MIR-text fixtures + object-diff vs `llc` (see §6) |
| Cross-block values | re-materialized at block boundaries (COPY from vregs) | plain vregs | plain vregs (LLVM model) |

## 4. What bcc should adopt (and not)

**Adopt:**
1. **The GlobalISel staging discipline**: translate mechanically to a
   generic-opcode MIR; legalize; select — as *separate, printable,
   testable stages*, rather than one fused AST/IR→bytes step. This is
   the single most valuable LLVM lesson here: each stage debuggable in
   isolation.
2. **TableGen's *concept*, not its implementation**: instruction
   definitions (name, operand forms, encoding hints, flags) live in one
   data table; selection patterns reference table entries by name. In
   bcc: a C++ `constexpr`-ish table in `machine_codegen.md`'s MI layer
   plus a pattern array. Avoid building a DSL.
3. **CGP's address shaping**: a small IR-level (or generic-MIR-level)
   pass that canonicalizes `gep`+load/store into base/index/disp triples
   so selection of memory operands is a lookup, not search.
4. **SDAG's proven pattern inventory for x86-64 integer code** (the X86
   `.td` files are the reference corpus): `lea` as add/shift-multiply,
   `test`-vs-zero instead of `cmp $0`, `setcc` + `movzx` for materialized
   compares, `imul r, r, imm`, `cdq`/`cqo`+`idiv` pairs, sign/zero
   extension folds into loads (`movsbl`), conditional-move selection for
   select-shaped IR.

**Do not adopt (for one target, at bcc's scale):** DAG-based matching and
its token-factor machinery (the block-local ordering freedom it buys is
what the *scheduler* will re-derive anyway; bcc can select in order);
TableGen itself; `ComplexPattern` generality; FastISel (GISel-style
stages serve −O0 fine); vector/AVX anything until scalar C is complete.

## 5. Concrete design for bcc

### 5.1 Shape

```
bcc::ir::Function
   │  (1) GenericLowering: IR → MachineFunction (generic opcodes)
   ▼
MachineFunction  { G_ADD, G_LOAD, G_ICMP, G_BR, G_ZEXT, ... ; vregs ; LLT }
   │  (2) Legalize: i1/i8/i16 int ops → 32/64-bit ops + explicit
   │      zext/trunc artifacts (fixed x86-64 rule: promote to 32)
   │  (3) AddressForming: gep/load/store → base+index+scale+disp
   ▼
   │  (4) Select: pattern table → x86-64 MachineInstrs
   ▼
selected MachineFunction → (scheduler?) → RA → PEI → emit via as/
```

`MachineFunction`/`MachineInstr` live in `machine_codegen.md` §5; here we
specify the selection stages.

### 5.2 Generic opcode set (stage 1)

One generic opcode per bcc IR opcode (drop `phi` — RA/PHI-elimination
owns copies at MI level, like LLVM), plus explicit `G_CONSTANT`
materialization and `G_IMPLICIT_DEF`. Translation is 1:1 and mechanical
(~300 lines), exactly IRTranslator's discipline. Types: reuse
`bcc::ir::Type` (it already has exactly LLT's scalar expressiveness:
`iN`, `float`, `double`, `ptr`, aggregates; aggregates lower to
`memcpy`-shaped G_MEMCPY-style ops or per-field ops — match what bcc IR
already does with aggregate load/store, introduce a
`G_MEMCPY`-style op so aggregates stop being register values, mirroring
real LLVM).

### 5.3 Legalize (stage 2) — the complete x86-64 rule set for bcc's types

- `i1/i8/i16` arithmetic/compare → widen to `i32`, result truncates where
  the C type demands (`G_TRUNC` artifact) — this is exactly what
  `LegalizeIntegerTypes.cpp`'s `PromoteIntOp_*` does for x86.
- `i64` ops: legal (x86-64).
- `float` ops: widen to `double`? **No** — keep `float` ops and select
  SSE `addss` etc.; x86-64 has both. (LLVM keeps f32 native too.)
- division/remainder by constants: leave as `div` initially; magic-number
  multiplication (`TargetLowering::expandDivisionByConstant`,
  implemented for x86 in `X86ISelLowering.cpp`) is a later optimization
  pass, not legalize.
- No vectors, no soft-fp, no atomics in scope → the rule table is ~10
  entries, hand-written.

### 5.4 Address forming (stage 3)

Recognize and *consume* these shapes into a `MemOperand {base, index,
scale∈{1,2,4,8}, disp, is_rip}`:
`G_GEP(base, idx)` × (scale by type size), `G_GEP(base, const)`,
`G_ZEXT`/`G_SEXT` of the index (x86 sign/zero-extends index registers for
free in ModRM/SIB — encode choice here), `G_TRUNC`-free disp arithmetic.
This is CGP's `optimizeMemoryInst` reduced to its core, operating on
generic MIR instead of IR GEPs.

### 5.5 Pattern table (stage 4)

```cpp
struct Pat {
  unsigned match(GenericInst);        // returns score or kNoMatch
  void build(MachineIRBuilder&, GenericInst);  // emits selected MIs
};
```

Ordered by priority; first-match-wins with specificity ordering
(more-constrained patterns earlier), mirroring how TableGen's emitter
orders patterns. Seed inventory (each traceable to an X86 `.td`
counterpart):

| Generic | x86-64 selection | X86 reference |
|---|---|---|
| `G_ADD i32/i64` | `add r/m, r` or `lea` when feeding address math | `X86InstrArithmetic.td` |
| `(G_MUL (G_SHL x, k)) + y` | `lea (y, x, k)` | `def : Pat<(add GR64, (shl…))` |
| `G_ICMP + G_BRCOND` | `cmp`+`jcc` (or `test`-vs-0) | `X86InstrCompiler.td` |
| `G_ICMP` as value | `setcc r8` + `movzx` | `X86InstrCMovSetCC.td` |
| `G_SELECT` scalars | `cmov*` (O1+) / branch pair (O0) | `X86InstrCMovSetCC.td` |
| `G_Mul + imm` | `imul r, r, imm8/32` | `X86InstrArithmetic.td` |
| `G_SDiv/G_SRem` | `cqo`/`cdq` + `idiv` | `X86InstrCompiler.td` brcond/div patterns |
| `G_ExtLoad` (sext/zext + load) | `movsbl/movzbl/...` | load folding patterns |
| `G_Store/G_Load` | `mov` with §5.4's MemOperand | `X86InstrInfo.td` |
| `G_FAdd/...` | SSE `addss/addsd`... | `X86InstrSSE.td` |
| calls | SysV: reg-classified args (rdi,rsi,rdx,rcx,r8,r9,xmm0-7), stack args, AL=varargs FP count | `X86CallingConv.td`, `X86ISelLoweringCall.cpp` |

The call row is the largest single item and is specified in
`machine_codegen.md` §5 (it is really ABI lowering, not selection).

### 5.6 What stays out of the selector

Flags-based CSE (`EFLAGS` liveness), tail-duplication feeding selection,
`X86FixupLEAs.cpp`-style post-selection LEA cleanup (x86's
`X86OptimizeLEAs`, renamed `X86FixupLEAs.cpp` in recent LLVM — verified
in the target directory), `X86FixupBWInsts.cpp` byte-width fixups —
these are *machine passes*, sequenced in `machine_codegen.md`, not
selector concerns.

## 6. Testing strategy and success criteria

- **MIR fixtures**: after each stage, `MachineFunction` prints
  (LLVM-MIR-inspired text); unit tests are exact-match fixtures per
  pattern (e.g. the `(shl)+add→lea` case above).
- **Object-level differential**: compile the same function with bcc's
  native path and with `llc -O0` and compare *executed behavior*, not
  bytes; byte-diff rate is a tracked metric, not a gate (instruction
  choice differs legitimately).
- **Per-pattern coverage tests**: every row in the pattern table has at
  least one C source exercising it, in the style of the existing
  regression corpus (clang-diff compatible).
- **Success criteria, Phase "ISel-0"** (roadmap M3): all scalar C int/FP
  programs in the corpus select, RA (naive), and *execute correctly*
  through bcc's own `.o` path with zero reliance on `llc`; instruction
  counts within 2× of `llc -O0` (measured via `as/` symbol/section
  sizes); MIR printers stable enough to be golden-file tested.

## 7. Challenges and trade-offs

- **Ordered (non-DAG) selection** can't exploit reassociation across
  instruction boundaries (SDAG's core win). Mitigation: the optimizer
  (`ir_optimizer.md`) canonicalizes shapes *before* the backend, and the
  address-forming stage handles the biggest single win (`lea`). Accept
  worse-than-LLVM code by construction; the goal is correctness +
  learnability first.
- **No TableGen** means encoding knowledge lives with instruction
  definitions in C++ tables — acceptable at ~100 x86-64 instructions for
  C; revisit only if a second target ever appears.
- **Aggregate ABI**: moving off `llc` changes aggregate passing from
  "whatever LLVM did" to bcc's own SysV classification — must be
  specified and tested against the psABI test vectors *before* enabling
  (called out in `machine_codegen.md` §7).
- **Varargs** require `va_start` area setup (register save area, gp/fp
  offsets) in the prologue and `va_arg` lowering — the frontend gap
  (bcc's `<stdarg.h>` deliberately defines no `va_start`) meets the
  backend here; roadmap M5.
